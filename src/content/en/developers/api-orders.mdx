Orders, cart and bookings cover the purchasing flow.

## Cart (`/api/cart`)

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/cart/add` | JWT | Add/increment item |
| GET | `/cart` | JWT | Get cart with product details |
| PATCH | `/cart/:id` | JWT | Update quantity |
| DELETE | `/cart/:id` | JWT | Remove item |
| POST | `/cart/clear` | JWT | Clear cart |

<Callout type="note">
The `/api/cart` HTTP endpoints are currently **frozen** — the router is not mounted in `app.js` (cart is frontend-held). Authenticated checkout still reads items from the `CartItem` table. See the [data model](./data-model).
</Callout>

### Suborders

Checkout splits the order into one **suborder per vendor business** (see [data model](./data-model)). Each suborder has its own `status` and `recipientCode`. Mutations that act on one vendor's share accept an optional `suborderId` so the backend targets the correct suborder instead of the whole order:

- `PUT /orders/:id/status` → body `{ "status": "confirmed", "suborderId": "..." }`
- `PUT /orders/:id/verify-recipient` → body `{ "recipientId": "<recipientCode>", "suborderId": "..." }`
- `POST /orders/verify-qr` → body `{ "orderId": "...", "suborderId": "...", "recipientId": "<recipientCode>" }`
- `PUT /orders/:id/deliver` → body `{ "recipientId": "<recipientCode>", "suborderId": "...", "collectedAmount": 15000 }`
- `PUT /orders/:id/negotiate` → body `{ "negotiatedAmount": 14000, "suborderId": "..." }`
- `POST /delivery/assign` → body `{ "orderId": "...", "deliveryPersonId": "...", "suborderId": "..." }`
- `PUT /delivery/:id/verify` → body `{ "recipientId": "<recipientCode>", "suborderId": "..." }`

The **delivery QR payload** encodes the suborder as `{ v:1, o:<suborderId>, r:<recipientCode>, s:1 }` — clients render it as a QR code and verification endpoints resolve `o`/`r` back to `suborderId` + `recipientId`.

### Checkout body

```json
{
  "hasDelivery": true,
  "deliveryAddress": "Kijitonyama, Dar es Salaam",
  "deliveryLat": -6.79,
  "deliveryLng": 39.22,
  "deliveries": [
    { "businessId": "...", "hasDelivery": true, "deliveryLocation": "Mikocheni" }
  ]
}
```

`deliveries` is an optional per-business array that overrides delivery per suborder. A `deliveryLocation` must be served by the business's delivery zones; otherwise the business's flat `deliveryFee` applies.

### Cash on Delivery

When the `payment_service` feature is **off**, online payments are disabled but ordering and checkout keep working. Checkout responds with:

```json
{
  "message": "Order placed successfully",
  "order": { ... },
  "requiresPayment": false,
  "escrowCreated": true
}
```

- `requiresPayment: false` → no gateway payment is expected; the order is placed as **Cash on Delivery** and the delivery agent collects on handover.
- `escrowCreated` → the escrow record is still created (default), so funds collected at delivery are held and released per suborder when verified.
- When `payment_service` is **on**, `requiresPayment: true` and the gateway payment (ClickPesa) is initiated instead.
- `POST /orders/:orderCode/pay` returns `{ "requiresPayment": false }` with a COD notice when `payment_service` is off.

### Order statuses

`pending` → `confirmed` → `shipped` → `delivered` | `cancelled`

- Confirming a suborder generates its `recipientCode` (used for the 3-way delivery verification and the QR payload).
- Delivering a suborder records `collectedAmount` (defaults to `negotiatedAmount ?? subtotal`), releases that suborder's escrow share and credits the business.
- Cancelling (customer or guest) is only allowed while `pending`/`confirmed`; it sets `cancelReason` on the order and suborders and refunds escrow.
- `returned` is accepted only via the admin route (`PUT /admin/orders/:orderId/status`).

<Callout type="note">
Multi-vendor orders generate one **recipient code per suborder**, verified against the matching business's share. `OrderItem` rows carry variant snapshots (`variantId`, `variantName`, `variantType`) plus `selectedSpecs`/`notes`.
</Callout>
