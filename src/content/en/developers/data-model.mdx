SokoPlus stores everything in **PostgreSQL** and models it with **Prisma**. This page covers the core models.

## Identity & roles

| Model | Purpose |
|-------|---------|
| `User` | Account with a `Role` enum, verification flags, soft-delete |
| `BusinessProfile` | Vendor/provider business record, 1:1 with a user, has a status |
| `DeliveryPerson` | Delivery team members linked to a business + user |
| `Region` / `University` | Tanzania regions and campus contexts |

## Commerce

| Model | Purpose |
|-------|---------|
| `Product` | Physical goods with price, stock, metrics, soft-delete. Images live on the product as an `imageUrl` string array (no separate image model) |
| `ProductVariant` / `WholesaleTier` / `ProductSpecification` | Product variants (type, name, price, stock, SKU), bulk-pricing tiers and spec key/value pairs |
| `Service` | Professional services with base price |
| `Category` | Single shared category tree for products and services (hierarchical via `parentId`, typed via `type`) |
| `Order` / `OrderItem` / `OrderSuborder` | Orders split per business with per-suborder delivery data, recipient codes and QR payloads |
| `CartItem` | Cart line items (product + optional variant). The cart itself is frontend-held |
| `Booking` | Service bookings with accept/reject + booking code |

| `FlashSale` (+ `FlashSaleParticipant`) | Time-limited deals |

## Communication

| Model | Purpose |
|-------|---------|
| `Message` | Direct messages between users |
| `Notification` | System notifications |
| `SupportTicket` | Customer support threads |
| `CustomerReport` | Bug/complaint/feature reports |

## Suborders

An `Order` can contain items from several vendors in one checkout. At creation it is split into one `OrderSuborder` **per business**; each suborder owns its own fulfilment lifecycle:

| Field | Purpose |
|-------|---------|
| `orderId` / `businessId` | Parent order and owning business |
| `subtotal` | Sum of that business's items |
| `status` | Own `OrderStatus` value per suborder |
| `recipientCode` | Unique code for the 3-way delivery verification of this suborder |
| `negotiatedAmount` / `collectedAmount` | Negotiated price and cash collected on handover |
| `hasDelivery` / `deliveryCost` | Delivery flag + fee per suborder |
| `deliveryPersonId` / `deliveryVerified` / `deliveryVerifiedAt` | Assignment + verified handover |
| `deliveryLocation` / `deliveryLat` / `deliveryLng` | GPS handover point |
| `cancelledAt` / `cancelReason` | When and why the suborder was cancelled |

A single order may therefore show multiple statuses and recipient codes at once. The delivery QR payload encodes the suborder: `{ v:1, o:<suborderId>, r:<recipientCode>, s:1 }` — verify endpoints accept `suborderId` + `recipientId` to target the right suborder.

Order-level fields also exist for legacy/single-vendor flows and order-wide accounting:

| Field | Purpose |
|-------|---------|
| `deliveryVerified` / `recipientId` | Legacy single-vendor delivery verification |
| `negotiatedAmount` / `collectedAmount` | Order-wide negotiated price and collected cash |
| `cancelReason` | Why the order was cancelled |

`OrderItem` rows snapshot the product at purchase time (`productId`, `productName`, `productPrice`, `quantity`, `imageUrl`) plus the selected variant (`variantId`, `variantName`, `variantType`) and any `selectedSpecs` / `notes`. Every item is linked to the owning suborder via `suborderId`.

Endpoints that act on one business's share (`/orders/:id/status`, `/orders/:id/verify-recipient`, `/delivery/assign`, `/delivery/:id/verify`) accept an optional `suborderId` to target the correct suborder.

## Soft delete pattern

Most models have `deletedAt` + `deletedBy`. Deleting sets those fields; normal queries exclude them. Admins can restore or permanently remove via `/admin/records`.

## Enums

| Enum | Values |
|------|--------|
| `Role` | `client`, `vendor`, `service_provider`, `delivery`, `partnerAdmin`, `majorAdmin`, `superAdmin` |
| `PaymentStatus` | `unpaid`, `paid`, `refunded`, `partial` |
| `TransactionStatus` | `pending`, `success`, `failed`, `refunded`, `held`, `released` |
| `PayoutStatus` | `pending`, `processing`, `completed`, `failed` |
| `PaymentGateway` | `selcom`, `stripe`, `tigo_pesa`, `mpesa`, `airtel_money`, `bank_transfer`, `clickpesa`, `other` |
| `EscrowStatus` | `held`, `released`, `refunded`, `expired` |
| `SubscriptionTier` | `free`, `pro`, `business`, `enterprise` |
| `SubscriptionType` | `vendor`, `service_provider` |
| `BoostType` | `pin`, `featured`, `spotlight` |

Business and order statuses are **plain string fields**, not Prisma enums: `BusinessProfile.status` uses `APPROVED`, `PENDING`, `REJECTED`, `SUSPENDED`; `Order.status` and `OrderSuborder.status` use `pending`, `confirmed`, `shipped`, `delivered`, `cancelled` (`returned` is also accepted via the admin route).
